# M2 下一小步：持续超限确认

## 实际规则

单设备 motor-a / temperature，教学配置，不代表设备安全标准。

| 已有状态 / 新观测 | 处理 |
| --- | --- |
| 未报警，首个有效温度 >80℃ | 开始 pending（待确认），累计0秒 |
| pending，后续温度 >80℃ 且间隔≤容忍值 | 使用单调时钟累计；新样本使累计≥5秒时正式触发 |
| 未报警，温度≤80℃ | 取消pending，回到无未解除告警 |
| pending，通信失败、长间隙或采集器重启 | 取消本轮累计；下次超限重新开始 |
| 已active，新有效温度<78℃ | 恢复，保存恢复证据 |
| 已active，温度≥78℃、通信失败、过期或重启 | 保留未解除记录；失败/过期/重启后未评估时当前未知 |

**5秒不是5个样本。** 例如在0/1/2/3/4秒收到5次高温，仍只有4秒；第5秒的新高温样本才可触发。若没有新样本，等待再久也不会自动触发。连续观测只说明采样证据满足约束，不证明两个采样时刻之间的物理温度始终超限。

容忍间隔 `max_gap_seconds = 1.5 × interval`，等于容忍值允许连续，大于才重置。默认 interval=1秒，容忍1.5秒。采集器只允许 `0 < interval ≤ 10/3秒`，否则在建库之前报参数错误，保证容忍值≤默认5秒新鲜度阈值。

**配置约束：** API 的 `--stale-after-seconds` 必须≥采集器的 `1.5×interval`；本步各进程不跨进程协商配置，请按此约束运行。默认组合1秒/1.5秒/5秒符合要求。同库只运行一个新版采集器；每次启动生成新会话，旧会话的成功/失败写入均拒绝并回滚，旧进程随后停止。

## 时间、事务与重启

- `time.monotonic()`用于持续时长与样本间隔；UTC只用于显示采集证据，系统时间跳变不会提前或延迟单调计时触发。若UTC回拨，页面可保守显示未知，因为原有最新测量查询按UTC排序；不是继续宣称当前已知。
- pending状态保存在数据库的同一写事务内，不使用需要单独回滚的内存累计。测量、告警和评估状态一起提交或回滚。
- 失败事件与清pending同事务，任何一项失败都不提交。采集启动清pending和评估位置，但不清active。
- 无样本时，API不会为了“过期”写库。pending可保留最后的历史证据；当年龄超过容忍值，current为unknown。下一条新样本才在写事务内完成长间隙重置。
- 页面只显示后端返回的 `pending.elapsed_seconds`，不自行增加；样本年龄超过间隔容忍、轮询延迟或API失败时隐藏可用累计，显示当前未知。前端约2秒查询，因此pending可能在两次查询之间短暂显示未知，这是按已取得证据保守处理。

## 持久化与兼容

`started_at`继续表示正式触发时间，原字段含义不变。新告警额外保存：

- `first_exceeded_at`、`first_exceeded_measurement_id`、`first_exceeded_value`：这一轮首次超限证据。
- `confirm_seconds`：当次最低确认时长（5秒）。
- `observed_seconds`：触发时实际已观测单调时长。
- `max_gap_seconds`：当次允许的最大样本间隔。

触发和恢复仍各有对应样本ID、温度与时间。旧即时告警迁移后 `confirm_seconds=0`；不编造首次超限、持续时长，原告警ID/触发/恢复证据逐字段保留。

迁移仅在新版采集器启动时执行。GET不建表、不加列、不回放旧测量。新API读取旧无告警表库显示not_enabled，读取旧即时规则库继续显示即时规则。前端新字段均可选，旧API响应仍可显示，不会因热更新崩溃。

接口仍为 `/api/devices/motor-a/latest` 的 `alarm` 和 `/api/devices/motor-a/alarms`。新增current=`pending`；规则增加confirm_seconds/max_gap_seconds；pending含首次超限证据与已累计秒。历史仍最近20条加总数，查询只读。
