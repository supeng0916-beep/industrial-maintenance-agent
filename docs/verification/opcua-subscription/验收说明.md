# M3：订阅通知、断线重建与重复投递防护

本步在原主动读取管道上新增明确的订阅模式。保留质量、源时间与温度告警规则，不承诺生产可靠性或断线历史补采。原有用户数据库、长期服务和独立实验未用于验收。

## 如何选择模式

```sh
# 主动读取对照，省略--mode时仍是read
uv run --locked python collect_opcua.py --mode read --port 4842 --db data/m3-subscription-practice.sqlite3

# 正式订阅：与上面的read二选一
uv run --locked python collect_opcua.py --mode subscribe --port 4842 --db data/m3-subscription-practice.sqlite3
```

同库电机B不能同时运行两种采集模式。切换时先停止自己启动的旧B采集器再启动新模式。数据库会话是最终写入边界：新会话接管后，旧会话不能写测量、诊断、状态或清除新会话的pending；电机A会话独立。

## 独立练习

先确认这些端口空闲；不关闭5191/8021/15041/4841或5180等现有练习服务。以下分别在根目录的新终端运行，选择新的练习库：

```sh
# A模拟器
uv run --locked python simulator.py --port 15042
# A采集
uv run --locked python collect_temperature.py --port 15042 --db data/m3-subscription-practice.sqlite3
# B模拟器，数值不变但每0.5秒生成新源时间
uv run --locked python opcua_simulator.py --port 4842 --value 85
# B订阅采集

# 只读API
uv run --locked python serve_api.py --port 8022 --db data/m3-subscription-practice.sqlite3
# 前端（另一个终端）
cd frontend
API_PROXY_TARGET=http://127.0.0.1:8022 npm run dev -- --host 127.0.0.1 --port 5192
```

浏览器打开5192，选电机B。85℃新源通知连续至少5秒触发教学告警；停止本次B模拟器可观察重连，同时A继续正常。用同端口重启模拟器，采集器自动创建新连接与新订阅。使用 `--value 77.9` 启动B，只有新的有效低温才能解除告警。

质量和源时间注入仍通过仅重启本次B模拟器切参数，不要求重启采集器：

```sh
uv run --locked python opcua_simulator.py --port 4842 --value 70 --quality bad
uv run --locked python opcua_simulator.py --port 4842 --value 70 --quality uncertain
uv run --locked python opcua_simulator.py --port 4842 --value 70 --source-mode missing
uv run --locked python opcua_simulator.py --port 4842 --value 70 --source-mode stale
uv run --locked python opcua_simulator.py --port 4842 --value 70 --source-mode future
uv run --locked python opcua_simulator.py --port 4842 --value 85 --source-mode frozen
```

每次同端口只运行一条模拟器命令。此版没有同进程在线修改源模式的控制接口。订阅模式下frozen且值/质量不变时，过滤器可能不再产生数据通知，只剩保活；随后因缺少新源证据清pending。它与主动read每秒重复读到相同源时间不同。

## 通知规则

使用持久Client、一个Subscription、一个MonitoredItem；按NamespaceURI解析节点，完整DataValue保留StatusCode及source/server/received时间。过滤为 `StatusValueTimestamp`、无deadband，所以相同温度但新的SourceTimestamp会发通知；不会以“值没变”去重。

请求发布/采样间隔默认250ms，服务端队列16，应用队列默认256。服务端实际修订的发布、采样、队列、保活和生命周期参数写入runtime并显示在页面；不能满足连续证据策略则明确停止，不静默退回只按值变化的过滤器。CLI可指定 `--publishing-interval-ms`、`--sampling-interval-ms`、`--server-queue-size`、`--queue-size`。

原准入门槛仍是Good、有限标量Double、非空新鲜且严格递增的SourceTimestamp。默认源年龄≤5秒，未来零容忍，依赖双方UTC同步；接收时间不代替源时间。订阅在取得SQLite写锁后按真实判定时刻再次检查源年龄，诊断分别保存received_at和decision_at，旧诊断decision_at可为空。接收时4.9秒、排队0.2秒的数据在判定时超过5秒，必须拒收；不能用接收时“曾新鲜”推进或解除当前告警。原本处于未来的源时间也不能靠排队等待变成合法。

### 两种“重复”

1. **同一通知重投递**：身份由采集session、连接generation、subscription id、Publish SequenceNumber以及通知/监控项索引组成。传输身份重复不新增有效测量或诊断，不推进或清除pending。旧连接回调失效，不得影响新订阅。
2. **新的通知、重复的源时间**：新的通知身份仍被处理，但源测量并不新，诊断拒收并立即清pending、保留active。这是已确认的保守策略，不是“重复只不推进，等超时才清”。不能仅依据温度数值区分这两者。

低层Publish回调直接提取序号，避免稍后异步处理时读取已变化的“最近序号”。投递身份去重与测量/诊断/告警在同一个数据库事务中提交，写失败不会先留下“已处理”标记。跨连接初始值仍受持久化源时间水位约束，旧源不能变成新测量。

## 保活、故障与恢复

保活只证明订阅有响应，不是有效温度，也不增加5秒告警证据。页面分别显示采集链状态、最近发布响应（含保活）、数据通知、质量和源新鲜度。runtime每秒量级刷新，超过5秒未更新时只读API和页面显示未知；stopped/failed作为明确终态保留。新世代在取得自己的诊断前，不借用旧世代有效温度恢复“可参与告警”。

通知回调不执行SQLite，应用队列有界，由专用数据库线程按序写入。应用队列满、服务端显式Overflow位、通知序号缺口等必须记录证据中断，清pending保active；不悄悄补零或把积压当即时数据。已经取出的通知若超过处理延迟上限（默认1.5秒），保存原始接收/判定时间及notification_processing_delay拒绝诊断、清pending保active，再丢弃积压并重连；重复传输身份仍优先忽略，不因旧投递时间重复清pending。数据库写锁等待也计入处理期限。未逐条处理的队列溢出/清理以丢弃计数和中断事件记录，不伪造完整补采诊断。数据库失败停止采集并输出错误；若故障状态本身也无法写入，日志明确提示，API依靠心跳过期显示未知。

持续Bad/Uncertain或源不合格只使温度不可用，不会因质量问题反复重连；新源证据间隙超过允许值会记录evidence_interruption、清pending并继续保持订阅。真正的连接/发布活性失败才作为通信故障；队列/序号问题作为证据中断并重建订阅。

断线后销毁本次订阅/Client，创建新世代；退避1/2/4/5秒封顶，单次网络操作设置超时。故障持续时可继续重试，Ctrl+C退出会关闭自己拥有的订阅、连接和数据库线程，不关闭模拟器或A采集器。

本地asyncua 2.0.1模拟服务端的内部队列溢出可能只丢弃最旧值、不设置Overflow位。因此无Overflow标志不证明没有丢失；本步还检查应用队列、发布序号和源时间间隙。不能保证识别所有静默丢采，不能保证断线补采或端到端恰好一次传输。
