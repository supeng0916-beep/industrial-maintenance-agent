# 工业设备状态监测与智能运维助手：项目计划书

版本：v0.2 后续开发修订版  
日期：2026-09-17  
定位：基于软件仿真、真实协议通信的个人课程设计与求职作品。

## 1. 项目目标与已知条件

学习者具有数据科学和 Agent 项目经验，没有工业硬件；现已学习并实验 Modbus/OPC UA、采集存储、四测点、质量与源时间、持续超温和订阅恢复。后续独立设计本项目的 Agent 与 RAG，不复用其他方向的旧 Agent 项目。

最终演示：模拟电机正常运行 → 注入持续升温 → 协议采集与数据库记录 → 看板告警 → Agent 查询趋势和维护文档 → 输出可追溯的排查建议。

学习成果：能够解释并独立修改协议采集链路；能够定位地址、倍率、数据过期和断线问题；能够说明前后端与 Agent 的数据来源及责任边界。

用户已明确：时间灵活，以真正学会为主。因此按掌握程度推进，不设置压缩交付日期。本计划确定架构方向和分阶段验收。M4采用 LangChain 单 Agent、现有 FastAPI、只读业务工具与本地知识库；新增依赖需在实施时验证 Python 3.11 与当前锁文件兼容性后固定版本。模型运行方式及生成模型型号需讨论确认，不假定已具备API凭据或本地推理环境。

## 2. 开发方式选择

| 方式 | 优点 | 代价 | 本项目建议 |
|---|---|---|---|
| 理解与实验为主，AI辅助实现 | 学习与交付兼顾，能形成调试能力 | 需要按模块验收 | 当前采用 |
| 全部手写 | 对代码细节掌握充分 | 前端和样板工作占用较多时间 | 时间充足且希望系统补 Web 时采用 |
| AI 完成大部分实现 | 较快得到可运行展示 | 容易绕过协议与故障定位学习 | 适用于明确以交付为主的阶段 |

沿用实际协作约定：AI可完成代码，学习者重点理解、预测结果、运行实验和排错；不把亲自敲代码作为掌握标准，不要求背诵API。每次介绍关键代码，配一项可解释的验收。

### 2.1 人与 AI 的具体分工

| 模块 | 学习者负责 | AI 负责 |
|---|---|---|
| 项目设计 | 理解数据流，确认范围与验收 | 提供方案、比较取舍、检查遗漏 |
| Modbus | 第一次连接读取、地址与倍率解析、错误处理 | 解释示例、代码审查、辅助定位问题 |
| OPC UA | 建立一个变量、读取、订阅回调、重连后恢复订阅 | 解释 NodeId/命名空间，补充样板代码 |
| 数据库 | 设计一条数据记录，写入和查询时间范围 | 重复模型、索引与查询建议 |
| Web 后端 | 读懂并修改一个查询接口，理解前后端契约 | 接口实现与参数校验 |
| 前端 | 接通一个 API，解释加载、错误与离线状态 | 页面布局、样式、图表封装 |
| 告警 | 持续超限、恢复、去重规则 | 边界案例与测试辅助 |
| Agent | 定义工具语义、读懂一个工具、核对证据与失败情况 | 独立实现LangChain单Agent、工具包装、检索和展示 |
| 交付 | 亲自复现并讲解演示 | 文档整理、启动脚本、展示润色 |

### 2.2 每个任务的协作流程

1. 自己说明任务输入、输出、失败情形与验收条件。
2. 对新知识模块，先让 AI 解释概念和官方示例，再一起实现和验证最小功能。
3. 运行正常和失败场景；记录现象、预期和实际结果。
4. 请 AI 审查小范围差异，不一次生成整个项目。
5. 验收后提交一个可运行版本；仅有生成的代码不能视为完成。
6. 在学习记录中写下“我能独立修改什么、仍不理解什么”。

给 AI 的任务描述模板：当前里程碑；本次目标；已有接口；允许修改的模块；验收场景；需要报告的验证结果。核心学习任务加上“先给提示和解释，让我先完成一次实现”。

## 3. 技术架构

### 3.1 技术选型

| 层 | 建议技术 | 选择理由 |
|---|---|---|
| 模拟设备 | Python + PyModbus / asyncua | 与采集程序通过真实协议通信 |
| 采集 | Python 独立进程，两个协议适配器 | 保持采集独立于页面与用户问答 |
| 存储 | SQLite，MVP 用 Python sqlite3 | 本地低频演示易复现，能直接理解 SQL |
| 后端 | FastAPI，按设备/数据/告警/助手划分模块 | 延续 Python 技术栈，形成清晰 HTTP 接口 |
| 前端 | React + TypeScript + Vite + ECharts | 用单页看板练习 B/S 分工，AI 可辅助页面实现 |
| 异常判断 | Python 确定性规则 | 可解释，可通过模拟场景检验 |
| Agent | LangChain `create_agent` 单Agent | 在现有Python后端集成工具调用，不复用旧项目 |
| 文档检索 | multilingual-e5-small + Chroma本地持久化；保留BGE中文对照 | 已对真实英文资料/中文问题比较，E5作为后续实验起点；质量仍需改善 |
| 可选增强 | BM25、reranker、自定义LangGraph流程 | 仅在具体评测或流程需求出现后引入 |

保留本项目已经实现的React、TypeScript、Vite和ECharts。M4在现有看板加助手入口，不更换前端栈。

### 3.2 运行与模块边界

```text
Modbus 模拟电机 A ──TCP 轮询──┐
                            ├─ 采集进程 ─ 数据标准化/告警规则 ─ SQLite
OPC UA 模拟电机 B ──订阅─────┘                                  │
                                                              后端
                                                 ┌─────────────┴──────────┐
                                             查询 API               Agent 模块
                                                 │                  │      │
                                             React 看板        只读查询工具 文档检索
```

单仓库，分别运行模拟器、采集器、后端和前端开发服务。采集器负责测量值和告警写入，后端通过短查询提供数据。当前A/B分别运行采集进程，共用SQLite且按设备隔离会话与告警；M4保留单后端进程和低频小规模数据；SQLite 连接独立管理，避免跨线程共用连接，保持短事务，设置合理的 busy timeout；遇到锁竞争要显式处理。

页面每 2 秒通过 HTTP 获取最新状态；历史曲线限制时间范围和返回点数。Modbus轮询默认每秒一次；OPC UA正式模拟器每0.5秒更新源测量，订阅按实际通知处理。刷新页面或打开第二个浏览器不能启动新的采集任务。采集循环不放在用户请求处理函数中。

M1 只运行 Modbus；M3 才加入第二个协议适配器。两个模拟设备分别代表两种接入方式，最终映射到相同的数据模型。

### 3.3 前端范围

- M1：一个页面，设备名、当前温度、最近更新时间、最近 10 分钟曲线、连接状态。
- M2：增加电流、转速、运行状态及告警列表。
- M3：增加设备切换与协议标识。
- M4：增加助手侧栏，展示回答、证据时间范围、工具结果摘要与文档引用。

离线与数据过期应明确展示；保留的最后值必须附带时间和失效标记。

### 3.4 后端接口草案

| 接口 | 引入阶段 | 作用 |
|---|---|---|
| GET /api/devices | M1 | 设备列表、协议、在线与新鲜度状态 |
| GET /api/devices/{id}/latest | M1 | 当前测点、单位、质量与时间 |
| GET /api/devices/{id}/history | M1 | 按 metric/from/to 查询历史，限制范围与条数 |
| GET /api/devices/{id}/alarms | M2现有 | 设备告警；M4另补工具所需时间范围过滤 |
| POST /api/assistant/chat | M4 | 提交问题，返回回答和结构化证据 |

设备状态区分连接状态与数据新鲜度：能连接但持续没有新数据也不能显示为健康。M1 用配置中的 stale_after_seconds 判定过期，初始教学配置为 5 秒。

### 3.5 数据与配置契约

统一测量记录：device_id、metric、value、unit、collected_at、source_time（可空）、quality、protocol。时间统一使用 UTC，页面负责本地显示。

quality 是项目自身标准化字段；OPC UA 原始状态码可另存。Modbus 没有统一的源时间与质量字段，采集程序根据请求结果生成质量信息，不能冒充设备提供的状态。通信失败写采集状态/事件，不写 value=0 的伪测量；最后成功值保持原时间，不能当作新样本重复入库。

点位配置包含连接信息、寄存器类型与地址或 OPC UA 节点标识、数据类型、倍率、单位、采样/发布参数。OPC UA 使用命名空间 URI 解析索引，避免将易变化的 namespace index 作为唯一长期标识。

数据库现已包含 measurements、collection_events、temperature_alarm_state、temperature_alarms 和 OPC UA 诊断/运行状态等表；M4业务工具复用现有只读查询，不另建一套采集事实库。measurements 建立 device_id/metric/collected_at 查询索引。告警字段至少包含设备、规则、开始时间、恢复时间、状态和触发证据。

## 4. MVP 的明确边界

M1 是可运行的采集监控 MVP，完整题目中的双协议与 Agent 在 M4 集齐。

M1 只实现一个 Modbus TCP 模拟电机、一个温度寄存器、每秒采集、SQLite 持久化、最新值/历史查询、一个浏览器页面，以及基本超时与数据过期显示。

M1 验收场景：

1. 模拟器地址 0 的保持寄存器为 653，按倍率 0.1 解码；数据库和页面显示 65.3℃。
2. 模拟温度变化后，趋势图更新；从产生样本到页面显示的目标延迟不超过 5 秒，实际测量记录结果。
3. 停止模拟器后，页面不把历史值伪装为当前正常数据。
4. 重启后端，历史数据仍可查询；打开第二个页面不会使采集频率翻倍。
5. 学习者能解释从寄存器到数据库再到图表的每一步。

自动重连与告警在 M2 深化。M1 不包含 OPC UA、LLM、RAG、复杂登录权限、Docker 编排和预测模型。

## 6. M4：独立 Agent 与 RAG 设计

### 6.1 已采用的方向与选择项

- 采用LangChain `create_agent` 单Agent，复用本项目FastAPI/React以及采集事实库；不复用旧Agent项目。
- LangChain agent建立在LangGraph上。第一版使用高层接口；只有出现明确的流程分支、人工介入或恢复需求，才增加自定义图。
- Dify暂不采用：课程项目已有自建API和页面，再维护平台服务会增加对接和运行负担。
- 不增加多Agent、任务规划器、知识图谱、微调或新云端平台作为首版条件。
- 模型运行方式尚未选择：在线API或本机推理在M4.3前与用户讨论。随后选择支持工具调用的具体模型，核对成本、延迟、中文回答及结构化输出；不把“接口兼容”当作行为可靠的保证。
- 本次只修订计划，未安装模型/框架、未创建云资源、未启用外部追踪或购买服务。

### 6.2 两类证据与数据流

```text
设备状态 / 历史数值 / 告警 → 受限只读工具 → SQLite
维护说明 / 点位文档 / 排查步骤 → 文档检索工具 → Chroma
                                  ↓
                       LangChain单Agent组织答案
                                  ↓
                FastAPI → 看板助手：事实、限制、建议、引用
```

业务数值不整体向量化。最高/最低温度等统计由SQL或确定性程序计算，模型负责解释。检索文档不证明本次故障原因；“轴承损坏可能导致发热”不等于“本次轴承损坏”。告警仍由采集器确定性规则运行，Agent不能触发/解除告警或读写设备。

### 6.3 四个只读工具

| 工具 | 输入 | 输出与边界 |
| --- | --- | --- |
| get_device_status | device_id | 各测点最后有效值、单位、质量、采集/源时间、当前可信度与未解除告警；说明检查时刻 |
| query_metric_history | device_id、metric、start、end | 范围内有效样本总数、max/min、时间与采集缺口说明；统计全范围，展示样本可截断但必须标记 |
| list_alarms | device_id、start、end、状态筛选 | 告警起止、阈值、触发/恢复证据、未解除状态；区分历史总数与当前未解除数量 |
| search_maintenance_docs | query、可选设备/主题过滤 | 文档片段、文档ID、标题、章节、版本、chunk_id和检索依据；没有相关证据时返回空结果 |

工具只接受白名单设备/指标和有限范围，SQL使用参数化查询，不给模型任意SQL、shell、协议客户端或文件系统访问能力。第一版历史查询范围沿用不超过24小时；展示明细最多1000条，max/min/count必须从同一只读快照的完整范围计算，不得用这1000条代替全范围。状态/事件与统计使用短只读事务，禁止跨模型调用持有事务。

时间范围采用带时区的ISO时间并统一UTC。采集缺口根据协议、采集模式和已记录事件解释；订阅通知不能简单用“每秒一条”计算完整率。报告“已记录有效样本最高值”，不声称缺口期间也无更高温度。无样本返回count=0和null统计；查询失败独立报错，不伪装空结果。运行状态是枚举，返回状态次数/记录，不把数字最大值称为最高运行状态。

### 6.4 RAG第一版配置（作为评测起点）

| 环节 | 起步配置 | 验证与调整条件 |
| --- | --- | --- |
| 文档集 | 约5～10份自编中文Markdown，明确“教学仿真”，含设备/点位、告警规则、通信/质量/时效排查 | 规则与当前代码一致；来源、版本明确，修改文档会更新索引 |
| 切块 | 先按标题/段落，再按嵌入tokenizer长度控制；目标300 tokens、重叠40 tokens | 不拆散短规则及前提；长表拆成带列名/标题的行组；标题及前缀计入长度，检查不被模型静默截断 |
| tokenizer | 使用所选嵌入模型配套tokenizer | 不用jieba替换神经模型tokenizer，不提前给正文加分词空格 |
| 嵌入 | BAAI/bge-small-zh-v1.5本地基线，512维；查询指令按模型卡 | 嵌入窗口按模型配置（该基线512 tokens），实测中文/英文标识召回；更换模型需重建索引 |
| 向量库 | Chroma PersistentClient，本机磁盘 | 单后端进程使用，索引构建由独立显式命令执行，原始文档为可重建依据 |
| 索引与距离 | Chroma单节点HNSW，显式使用cosine，其他参数先默认 | 固定模型/归一化约定并记录；不跨不同模型空间混用向量 |
| 召回 | 初始top_k=5 | 少于5块返回实际条数；得分含义按距离约定，不能把相似度当正确率；无答案题校准拒答 |
| 元数据 | doc_id、title、section、version、chunk_id、内容hash、适用设备/主题 | 支持可追溯引用、内容更新与旧片段删除；不只依赖向量相似度判设备适用性 |
| 重排 | 默认关闭 | 只有召回已有正确片段但排序不佳时，再试候选重排模型 |

这组参数是小规模课程实验基线，不承诺在领域文档上最优。第一版不接扫描PDF/OCR和复杂上传管理；需要PDF时先评估解析与表格保真，不能直接把页文本乱切。

### 6.7 评测与验收口径

先建立约20题的小题集，标注允许调用的工具、正确设备/时间范围、需要的事实、相关文档章节和不能声称的结论。包含正常、超温、通信中断、Bad/缺源/过期、无历史数据、文档无答案、文档与现场不一致、查询失败及诱导修改设备等情形。

分三层报告：

1. 工具层：固定夹具验证数值、单位、全范围统计、隔离与失败语义；数值错误或越权为阻断项。
2. 检索层：检查top5是否包含标注相关片段、前提是否完整、是否误用其他设备文档；保存失败样例后再决定增强。
3. 回答层：每个数值和诊断事实可追溯到当次工具结果；引用指向真实片段且支持陈述；无证据不编造故障原因。重点边界题全部通过，再报告其余题的实际结果，不预写“100%准确”。

初始限制建议：每轮问题最多6次工具调用、每工具5秒查询期限、总回答60秒（模型网络超时也受总期限约束）。在M4.3按实际供应商能力验证；超限明确返回未完成和已取得证据，不继续无限循环。只保留短期当前对话上下文，不添加长期用户记忆。文档内容是证据，不可作为覆盖系统规则的指令。

### 6.8 M5：交付收尾

统一双协议和助手的启动/停止说明，标明所需模型配置、索引构建、数据路径和本地端口。模型或知识库不可用时监控采集仍可独立运行。用独立演示库完成正常→持续超温→断线→恢复→Agent查询与文档建议的完整演示。

课程报告包括架构、点位表、数据/API契约、协议差异、告警规则、RAG配置、工具/检索/回答评测、仿真及时间同步限制。演示截图/录像对应实际功能；不把重连成功称为无丢采，不把未确认原因称为故障诊断结论。最后保留学习者解释、修改和排错的验收记录。

## 7. 验收与风险管理

- 协议：固定已知原始值验证地址、倍率、单位；M2 加一个跨寄存器编码练习。
- 状态：模拟器停止/恢复后确认离线、过期、重连与订阅恢复行为。
- 告警：使用可重复时间序列验证持续阈值、解除条件和去重。
- 接口：检查时间范围、非法设备/指标、空结果、最大返回点数。
- 数据库：验证查询历史保留与短事务，处理忙锁错误，不让页面请求影响采集循环。
- 展示：从已知注入事件到页面变化测量延迟，报告环境和实际结果，不预写指标。
- Agent：工具超时、无数据和检索不到依据时，回答说明缺口。

不追求为了覆盖率而写大量重复测试；优先测试地址/数据转换、状态变化、告警时序和回答证据等易出错且有意义的行为。

主要风险：第三方 API 版本不匹配、AI 生成未经验证的代码、前端学习挤占协议学习、仿真数据被误述为工业实测。对应措施：锁定版本与示例；小任务逐项运行；核心知识优先；报告中明确仿真边界。
