2. 整条链路各自负责什么

组件职责常见误解
模拟器模拟 PLC 或温控仪的数据接口，通过真实协议提供数值仿真通信不等于真实电机物理过程
采集器读取、换算、记录时间、保存测量、运行告警规则页面刷新不是采集
SQLite保存测量、失败事件、告警及规则状态历史值不是当前实测值
后端 API从数据库查询并解释数据时效GET 查询不应启动采集或补写告警
前端显示温度、时间、数据可信度、趋势和告警API 请求失败不能直接断言设备断线
未来 Agent查询证据和文档，辅助解释与排查不让模型代替确定性告警规则

两个浏览器查看同一设备，只应增加查询请求，不应增加采集频率。关闭页面后，采集进程仍可独立运行。

3. Modbus：寄存器、地址、列表与倍率

PLC（可编程逻辑控制器）：工业控制器，依据输入和程序逻辑控制输出。模拟器目前只模拟其数据通信接口。

寄存器：Modbus 中一个通常为 16 位的数据单元。设备可以提供很多寄存器，具体代表温度、电流还是其他数据，由设备点位表约定；不是每个地址都有效，也不是所有值都必然变化。

保持寄存器（Holding Register）：Modbus 的一个数据区域，协议有读写功能；具体设备是否允许某地址写入，仍受设备实现限制。另有输入寄存器、线圈、离散输入。

response = client.read_holding_registers(10, count=3, device_id=1)
# 假设返回 [653, 120, 1500]
# registers[0] 对应地址 10
# registers[1] 对应地址 11
# registers[2] 对应地址 12

列表索引不等于寄存器地址。 本次从地址 0 开始，所以 registers[0] 恰好对应地址 0；从地址 10 开始就对应地址 10。count=3 表示读取三个寄存器，并不表示取三个历史时刻。

一个值可能跨多个寄存器，例如 32 位浮点数；还需要知道字节/字顺序。本项目已有版本只用了单个无符号寄存器。

raw = 653
scale = 0.1
temperature = raw * scale  # 65.3℃

Modbus 数字没有自动附带单位和倍率。两者来自点位约定。真实历史是采集器将多次读取结果按时间保存后形成的。

4. 成功、失败、历史和时间

情况应保存什么不能做什么
读取成功本次真实数值及采集时间仅因数值没变就认定重复数据
通信失败communication_error 事件填 0、复制旧值配新时间
读取成功但写库失败明确报告存储失败把它说成通信失败或已保存
长时间没有新记录提示数据过期，检查采集器直接断定传感器坏了

collected_at：本项目采集器记录的采集时间。source_time / SourceTimestamp：数据源提供的时间，可为空，不能捏造。ServerTimestamp：OPC UA 服务器关联的时间；ReceivedAt：客户端收到通知的时间。二者差值可能包含时钟偏差、排队和传输等因素，不能简单当作纯网络延迟。

UTC：统一存储时间使用的时间基准。+00:00 表示 UTC，上海通常显示为 UTC+8。例如 05:16:38+00:00 对应本地 13:16:38。

最后成功时间仅在成功读取后更新；最后尝试时间包括失败。数据年龄是现在减去最后成功时间，本项目默认大于 5 秒为过期。旧失败事件保留，不代表设备此刻仍离线。

-- 最新记录在前；同一时间用 id 辅助确定顺序
ORDER BY collected_at DESC, id DESC

用户实际完成：5 次成功写入 65.3℃；停止模拟器后产生 3 条失败事件，原温度历史不增加；重启模拟器后，同一采集器再次读到 72.8℃。

5. Modbus 与 OPC UA 对照

维度ModbusOPC UA
定位数据区域、地址、设备标识NodeId，命名空间及节点标识
返回内容位或寄存器，含义依赖点位表可携带类型、质量、时间及属性
获取方式本项目采用轮询可主动读取，也可订阅变化
单位与换算通常依赖外部约定可能有 EngineeringUnits 等元数据，仍需核对
历史采集后自己保存订阅队列不等于历史库；历史访问需服务器支持
安全本实验普通本地 TCP协议具备安全机制，本实验匿名 NoSecurity

Node（节点）：地址空间中的对象、变量或属性等信息元素。NodeId：用于标识节点，例如 ns=2;s=MotorA.Temperature。其中 ns=2 是命名空间索引，s= 后面是字符串标识。

Namespace URI：命名空间的稳定名称；客户端先用 URI 查当前索引，避免写死 ns=2。实验加入额外命名空间后，温度变为 ns=3，客户端仍能读取。稳定 URI 并不替代对节点标识和服务器配置的管理。

DataType=Double 表示双精度浮点数。不能仅凭它或单位属性就断言不需要缩放，需看变量定义。

EngineeringUnits 是可选的工程单位元数据。本实验并未提供该属性，因此输出明确写 UnitConvention=℃（文档约定，无EngineeringUnits属性）。

6. 数据质量不是设备健康

StatusCode 描述数据的质量/状态：Good、Uncertain、Bad 等；具体问题需要查看状态码。

  • Good：数据质量状态良好，不表示电机健康，也不证明传感器绝无问题。
  • Bad 或 Uncertain：不能只看数值小于 80℃ 就宣布温度正常。
  • 更合适的提示：显示最后数值及时间，并说明质量不可信，当前是否正常无法确认。

本项目 Modbus 的 quality=good 来自采集程序根据成功请求作出的标准化标记，不是假装设备返回了 OPC UA 质量码。

7. 订阅：采样、发布、队列和保活

采样间隔：服务器检查监视变量的节奏。发布间隔：订阅组织并向客户端发送通知的节奏。监视项（MonitoredItem）：订阅内具体监视的节点及其参数。队列：暂存采样捕获且符合通知条件的数据，大小和丢弃策略影响保留哪些通知。

数据源更新 → 服务器采样/过滤 → 监视项队列 → 订阅发布 → 客户端回调

缩短发布间隔，无法找回采样阶段已经漏掉的短时高温。增加队列也不能保存从未采到的值。传感器每秒才更新一次时，更频繁读取不等于获得更多独立测量。

Keepalive（保活）：说明订阅仍在响应，不是新温度测量，也不是传感器健康证明。

回调函数运行在我们的客户端/采集器程序里，程序退出后不会继续处理通知。重连后要考虑会话、订阅和监视项恢复，并避免重复创建导致重复处理。

“没有通知、主动读取成功”只能证明此次读取路径可用；可能没有满足变化过滤条件，也可能订阅异常，不能仅凭读取成功保证订阅正常。实验相同温度未通知，随后改为 73.5℃ 收到通知，才补充了订阅链路的证据。

实验输出 SourceTimestamp=null 时应保留未知，不能用 ServerTimestamp 或 ReceivedAt 冒充。请求会话超时 3600000ms、服务器给 600000ms，是协商后的超时值，不是看到提示就认定连接失败。

8. 告警为什么会抖动

如果 >80℃ 报警、低于80℃恢复，79.8、80.2、79.9、80.1 会使状态反复切换。

你提出使用平均温度，这是合理的平滑方法，但 70、70、90、70、70 平均只有 74℃，可能掩盖短时高温。采用哪种方法取决于设备风险和规则要求。

方法主要作用注意点
滑动平均平滑数值波动可能稀释尖峰、推迟触发
回差报警与恢复用不同阈值不解决首次短时超限立刻触发
持续超限要求满足一段时间才触发需要明确采样中断如何处理

回差（Hysteresis）：本项目超过 80℃ 触发，低于 78℃ 恢复。已报警后降到 79℃仍报警，恰好78℃也不恢复。未报警时恰好80℃不触发。

9. 告警是一段有开始和结束的事件

81℃ → 告警 #1 触发
79℃ → 告警 #1 保持
77℃ → 告警 #1 恢复并保留历史
81℃ → 新一轮符合触发条件后创建告警 #2

连续收到十次高温属于同一次告警，不应新建十条记录。告警状态持久化在数据库，重启先识别未解除告警；只在内存里保存会导致重启丢状态。

曾经回答的易错点：你正确判断第二次超温后总数为2，但认为两条都报警中。正确是 #1 已恢复、#2 报警中。历史总数与当前未解除数量不是同一指标。

已报警后通信失败：保留未解除告警，同时提示当前温度未知；不能说已经恢复，也不能把旧85℃称为当前温度。

10. 事务：把有关联的修改一起保存

事务（Transaction）把一组数据库操作作为整体。提交（COMMIT）保存整个事务；回滚（ROLLBACK）撤销本次未提交的修改。

# 教学伪代码：异常应向外抛出，使上下文回滚
with conn:
    measurement_id = 保存本次温度(85)
    更新告警及评估状态(measurement_id, 85)

如果保存告警失败，本次温度插入也应撤销，之前已提交的历史不受影响。设备读取可能成功，但本轮存储失败，需要单独报告。失败事件和取消待确认状态也需要在同一事务里完成。

事务只包含短数据库操作，不要把网络请求或 sleep 放进去长时间持锁。

11. 持续超限：5秒不等于5个样本

最终教学规则：有效温度持续超过80℃，连续观测累计至少5秒，才触发。期间≤80℃、通信失败、样本间隔过长或采集器重启，都取消待确认计时。

00秒 第1个高温样本 → 累计0秒
01秒 第2个高温样本 → 累计1秒
02秒 第3个高温样本 → 累计2秒
03秒 第4个高温样本 → 累计3秒
04秒 第5个高温样本 → 累计4秒
05秒 第6个高温样本 → 满足5秒，可触发

默认每秒采集，允许相邻样本间隔不超过1.5秒。这个1.5秒是本项目容忍配置，不是协议标准。即使没有失败事件，10秒空白也会打断连续性。连续观测不能证明两个采样时刻之间的物理温度始终超限。

单调时钟（monotonic）用于计算持续时长，避免系统日历时间校准导致计时跳动；UTC用于证据日期。待确认计时不跨进程重启续用。

# 概念伪代码：实际实现还包含事务、采集会话和证据保存
if 读取失败:
    取消待确认()  # 已触发告警保持未解除
elif 已有未解除告警:
    if 新有效温度 < 78:
        恢复原告警()
else:
    if 温度 <= 80:
        取消待确认()
    else:
        if 首次超温 or 样本间隔过长:
            从本次样本重新计时()
        if 单调累计时长 >= 5:
            新建告警()

读取失败时先处理失败分支，不使用不存在的新温度；已触发告警保持未解除。

页面不能靠倒计时自行报警，必须等待后端处理新的有效样本。待确认已累计秒数仅展示已观测证据；没有新样本时保守显示未知。
