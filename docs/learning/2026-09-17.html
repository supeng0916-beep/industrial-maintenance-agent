折叠自测｜先想，再展开

85℃不变，但源时间更新，要丢弃吗？

不丢弃。按本模拟器约定它是新的源测量；仍需通过质量、时效和间隔校验。

4.9秒龄的数据排队0.2秒，仍可参与吗？

不可。判定时已5.1秒，超过5秒门槛；接收时新鲜不等于处理时新鲜。

温度和电流写在同一事务，测量同步了吗？

没有。事务只保证数据库操作一起成功或回滚。

重复通知与新通知的重复源时间一样处理吗？

不同。相同传输身份忽略且不清pending；新身份但重复源时间按当前严格策略拒收并清pending。

最新状态能回答过去10分钟最高温度吗？

不能，即使最新值未过期也不够。需要历史工具对完整范围的有效样本统计。

文档说轴承损坏可能发热，能确认本次根因吗？

不能。文档提供可能解释和排查方法，实际原因需要更多现场证据。

2. 多测点与点位表

点位表定义地址、指标、类型、倍率、单位及业务含义。当前正式Modbus四点均为uint16：

地址指标倍率/解释默认原始值与结果
0temperature 温度×0.1℃653 → 65.3℃
1current 电流×0.01A123 → 1.23A
2speed 转速×1rpm1450 → 1450rpm
3running_state 运行状态0停止、1运行1 → 运行

从0读取count=4时，列表四项对应四个寄存器。这四点恰好各占一个寄存器；后面的32位练习会说明“一个寄存器不一定是一整个测点”。

枚举：数字与状态含义的约定。正式版本仅0/1；前面举过“2＝故障”的例子，但未采用。2和7都是当前点位表未定义的值，不是通信失败。

用户判断：收到7应显示未知。补充准确表达：当前状态未知，原始值7，数据校验失败；协议已返回响应。 当前实现把该原始证据写入事件，不写入有效测量表。

3. 整轮事务与独立测点状态

一次读四点，保存时形成四条不同metric的记录。当前业务契约要求整轮完整提交，温度告警也包含在同一事务里。

# 教学伪代码；网络读取放在事务外
values = 读取并校验四点()
with conn:
    保存温度(values)
    更新温度告警(values)
    保存电流(values)
    保存转速(values)
    保存运行状态(values)
# 任一写入异常向外抛出，本轮全部回滚

今天你最初选择“电流保存失败，保留温度”。这是另一种可行设计，但与本项目“整轮完整保存”的约定不同；这里必须回滚。不是所有系统都必须采用整轮事务。

查询以 device_id＋metric 定位。只查“最新记录”而不限定metric，可能拿到1.23A却显示成1.23℃。数值、指标、单位应一起传递。

各测点用自己的最后有效时间判断新鲜度：温度2秒、电流11秒，不能因为温度新鲜就称电流也新鲜。我们当前整轮保存通常时间一致，旧库缺测点或以后采样节奏不同仍需分别判断。

4. 零、未知与校验失败

情况含义处理
完整返回电流原始0真正读到了0可保存0A，但不保证传感器物理测量准确
读取失败后补0没读到，却伪造数值禁止
请求4寄存器只返回3数据不完整整轮失败，不补缺失值
状态寄存器返回7响应成功、业务含义未定义data_validation_error，保留原始证据，整轮不入库

当前实现中校验失败会取消温度pending，保留active；其他三点即使数字看起来合理，也不能绕过整轮契约。整轮拒存是项目选择，不是Modbus协议强制要求。

三个成功不能混为一谈：通信成功、存储成功、物理测量准确。

5. 多测点推理：关联不是因果证明

场景：状态“运行”、电流0A、转速0rpm。

你选择先核对点位与测量来源，这是正确方向。地址可能读错；也可能“运行”实际表示运行指令已发出，而非电机确已转动。

转速不能直接证明电流传感器损坏，但也不是完全无关。多个可信测点可以帮助缩小排查范围，仍需点位含义、时间、质量和现场证据。

核对顺序：设备/地址是否正确 → 点位代表指令还是反馈 → 数据时间是否可比较 → 再提出可能解释。不能把“可能原因”直接写成“已确定原因”。

6. 同一轮读取不等于同步测量

设备可能分别更新各寄存器。批量读到四个值、写入同一个collected_at，只表示我们在同一轮取得并记录。

层次能说明什么
设备测量时间数据源何时生成测量；需了解时间戳含义/同步机制
采集时间采集器何时取得数值
数据库事务相关写入是否一起成功或一起撤销

事务不能让不同传感器“变同步”。温度每5秒更新、采集器每秒读一次，连续5次相同值不等于5次独立源测量。你已准确复述：不能仅凭批量读取证明同步。

7. 跨寄存器编码：范围、精度和顺序

一个Modbus寄存器16位，按无符号整数解释范围0～65535。倍率0.001时最大表示65.535℃，要表达123.456℃，整数原始值123456需要更多位。

32位值占两个寄存器。若温度占地址0/1，电流不能独立再占1，应从2开始。读三个寄存器可能只对应两个完整测点。

# uint32，点位表约定高16位在前
registers = [1, 57920]
raw = registers[0] * 65536 + registers[1]  # 123456
temperature = raw * 0.001                 # 123.456℃

也可能是IEEE754 Float32，此时同一组比特应按浮点格式解释，而不是把整数直接当温度。

import struct
registers = [0x4282, 0x999A]
raw_bytes = struct.pack('>HH', *registers)
temperature = struct.unpack('>f', raw_bytes)[0]

HH是两个16位无符号整数；f是32位浮点；本例 > 指定大端字节顺序，列表顺序同时约定高16位字在前。字节顺序与寄存器字顺序分别核对。unpack后的[0]取返回元组的唯一结果，不是寄存器地址。

实际离线实验正确错误
uint32＋0.001123.456℃换字顺序：3795845.121℃
Float3265.300003051758℃，显示65.3℃换字顺序：约-1.595e-23℃
Float32误作uint32应按浮点解释得到1115855258

浮点小误差来自二进制表达。错误值不一定巨大，也可能看起来很小或合理。因此要用点位表＋已知测试值验证。超大温度优先查地址、类型、字节/字顺序、倍率，不能先断定设备真的几百万度。

OPC UA客户端已返回有类型的Float/Double数值，不必自己拆成寄存器重组，但仍要核对单位、缩放及业务含义。

8. OPC UA：通信、质量、新鲜度三道判断

数据记录与展示当前温度告警
Good、有限标量、源时间新鲜且递增保存有效测量可参与
Bad/Uncertain保留诊断原始状态与时间不参与，取消pending，保留active
Good但源时间过旧标记源过期，保留诊断同上
源时间缺失source_time=null，说明测量新鲜度无法核实同上
源时间明显在未来时间异常同上

本实验B默认源年龄0～5秒，未来时间零容忍，假设双方UTC同步。这是保守教学策略，不是所有OPC UA系统的唯一规则。A的Modbus source_time=null有不同协议语义，不把B的门槛机械套给A。

你的回答“Good但旧数据不能用”正确；补充纠正：若这次请求确实返回响应，说明本次通信成功，不等于服务器未响应。旧源时间不能单独证明传感器坏了。

真实asyncua模拟器在Bad状态会将线上Value置Null，诊断保存实际收到的null，不把配置的70℃捏造为已收到的测量。

9. 四种时间与排队后重检

时间含义
SourceTimestamp / source_time数据源提供的时间，按本模拟器约定为测量生成时间
ServerTimestamp服务端关联时间，仅作独立诊断
received_at客户端真正收到通知的时间
decision_at取得数据库写锁后实际判断时刻

received_at不能填进缺失的source_time，也不能在出队时被重新盖成“现在”。12:00:00测量、12:00:01收到、12:00:21处理，判断时源年龄已21秒。

重要补充边界：接收时源年龄4.9秒，只排队0.2秒，判断时也超过5秒。开发据此补充了取得SQLite写锁后再次检查源年龄的逻辑和测试；先前仅限制排队1.5秒不足以覆盖此边界。

# 仅展示概念，完整代码另有未来/重复/质量/处理期限等校验
source_age = decision_at - source_time
if source_age > source_max_age:
    保存拒绝诊断()
    取消待确认()  # 不解除已有告警

同一时刻12:00+08:00等于04:00+00:00，要先统一UTC。时间戳比较依赖两端时钟；本地累计耗时使用monotonic单调时钟，避免校时跳变。

10. 两种重复与一次明确的策略修正

数值相同不代表重复：85℃/源12:00:00与85℃/源12:00:01，是不同源测量，质量/新鲜度合格可以继续计时。

本次实际实现的两种重复：

  • 同一通知重投递：按采集会话、连接代次、订阅ID、发布序号及项索引识别，忽略；不重复写入，也不清除新pending。
  • 新通知身份但源时间重复：按本项目严格准入拒绝，立即清pending，保留active。

早先教学曾说“重复源时间先不推进，间隔超限才清计时”。随后对照实现，明确第一版采用更保守的“重复源时间立即清计时”。两者不同；这份总结以当前实现为准，不能混用解释。

主动读取比源更新快时，严格策略可能频繁取消pending，是第一版限制。订阅采用StatusValueTimestamp过滤，源时间更新也通知，常值测量不会因值不变而全部消失。

11. 订阅恢复：代次、保活与队列

连接代次 generation：每次新连接尝试有新代次。旧代回调迟到时不能写当前状态。采集器session又提供跨进程写入隔离；同一B不可同时read和subscribe争写，A的会话独立。

# 概念：丢弃旧连接回调
if notification.generation != current_generation:
    return

保活 keepalive说明订阅仍有响应，不是测量，不能推进超温时间。revised参数是服务器实际接受的参数，可能不同于请求；本次实测发布250ms、采样250ms、服务端队列16、保活4、生命周期120。

两处队列：服务器监视项队列 → 网络 → 采集器应用队列 → 数据库线程。加大客户端队列找不回服务器已丢的通知，也不会自动提高处理速度。

应用队列默认256，有界；回调不直接写SQLite。溢出、序号缺口、处理积压记录证据中断，清pending保active。默认处理期限1.5秒，等数据库锁也计入；超期诊断保留真实received/decision，再丢积压重连。

本地asyncua服务端内部队列可能静默丢最旧项且不设Overflow位。没有溢出标记不是完整性证明；应用溢出、序号与源间隙检查仍无法保证检测所有静默丢失。

断线重建订阅，退避1/2/4/5秒封顶；不断立即重试会增加负担。重连成功不意味着补齐断线历史。项目没有工业生产可靠性或端到端恰好一次保证。

13. Agent：现象、原因与建议分开

查到85℃及持续告警，只证明记录到的超温现象，不能直接答“轴承损坏”。需要负载、振动、润滑、现场检查等更多证据区分原因；当前项目没有这些完整诊断证据。

查询工具告诉Agent“这台设备记录了什么”；维护文档告诉它“这种现象通常可检查什么”。文档写“轴承损坏可能导致发热”不证明这次轴承损坏。

已观测事实：B有持续超温告警，触发值85℃。
证据限制：当前数据若已过期，当前温度未知。
可能解释：仅列文档支持的可能性，不作确定诊断。
检查建议：引用相应维护章节，并注明教学仿真适用范围。

工具只读：模型不能执行任意SQL、写设备、解除告警或运行shell。模型不可用不应阻断采集与确定性告警。

14. 历史统计：完整范围，不是最新值或截断片段

你正确回答“只查最新状态不够”，但最初理由是“最新值过期”。关键纠正：即使最新值很新，也不能知道过去10分钟最高值；需要历史范围查询。旧样本现在过期，不使它在过去时间段内的历史证据失效。

全范围统计与有限明细分开：1002条记录只展示10条，max/min也必须算全部1002条。今天开发CLI测试确实覆盖了截断外的-10和999极值。

结果正确返回
查询成功，有样本全范围count/min/max，附范围及明细截断标记
查询成功，0样本count=0，min/max=null；不是0℃
数据库不可读或超时结构化error；不是“没有记录”

统计只表示已记录有效样本的最高温度，不等于物理设备真实峰值。缺口期间可能有未观测的更高值。订阅不能用固定每秒一次随意推算完整率。

当前工具按collected_at起止闭区间筛选quality=good，B的collected_at是接收时间；并非按source_time范围筛选。最大跨度24小时。运行状态是枚举，统计各状态次数，不能把max(0,1)当作物理极值。

工具作用
