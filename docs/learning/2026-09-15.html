学习笔记 / 02

名词速查：知道它是什么，也知道它不是什么

优先理解职责与边界；不要求背诵库 API。下表也收录了阅读项目文件需要的基础词。

PLC 可编程逻辑控制器

工业现场执行控制程序的控制器。典型循环是读取输入 → 按程序判断 → 更新输出。

注意：例如读取温度后，按预设条件输出风扇控制信号；不是大语言模型。

传感器 把物理量变成可读取的信号

温度传感器测温；控制器通过相应接口获得读数。

注意：传感器不一定直接提供 Modbus TCP 接口。

温控仪 / 变频器 / 网关 可能提供设备数据的硬件

温控仪用于温度监测与控制；变频器用于电机驱动控制；网关可连接、转换设备通信。

注意：它们是否支持 Modbus、哪些地址可读，要查具体设备手册。

模拟器 软件扮演设备通信端

本项目在内存中保存一个数，通过 Modbus TCP 提供给客户端。

注意：目前模拟数据接口；没有完整模拟 PLC 控制逻辑或电机发热过程。

采集器 主动读取并处理设备数据的程序

目标是按节奏读取、转换、保存测量值，并记录采集状态。

注意：当前 read_temperature.py 只是一次性读取程序，还没有循环或数据库。

Modbus TCP 通过 TCP 传递读写设备数据请求的协议

客户端按设备编号、数据区、地址和数量请求数据，服务端返回结果。

注意：协议响应中的寄存器值不自带本项目的温度倍率和单位。

服务端 / 客户端 等待请求的一方 / 主动请求的一方

模拟器是服务端，读取程序是客户端。

注意：角色与运行在哪台电脑无关；两者可以运行在同一台电脑上。

IP / 回环地址 找到网络端点所在主机

127.0.0.1 表示本机，用于这次实验。

注意：端口 15020 则用于找到本机上对应的 TCP 服务。

端口 定位主机上的服务端点

本项目两端都使用 TCP 端口 15020。

注意：它不是寄存器地址，也不是设备 ID。

设备 ID Modbus 请求中的设备标识

本实验服务端配置设备 1，客户端使用 device_id=1。

注意：通过网关等场景可能区分不同设备；它不是 IP 地址。

寄存器 / 地址 16 位的数据格子 / 格子的编号

读出的数如何解释，取决于设备点位表。当前按无符号整数解释，范围为 0～65535。

注意：不是每个格子都不断变化；一个较大的数也可能占多个寄存器。

保持寄存器 Modbus 的一种 16 位数据区

协议支持读取和写入；本项目只读。读取方法为 read_holding_registers。

注意：“保持”不保证断电保存。具体设备可写范围和权限以手册为准。

点位表 设备数据的说明书

定义设备、数据区、地址、类型、倍率、单位等对应关系。

注意：地址 0 没有天生的温度含义；当前约定它代表温度。

原始值 / 倍率 / 单位 设备数值 / 转换约定 / 数值意义

653 × 0.1 = 65.3℃。

注意：换倍率不会自动让设备改变数据编码，必须与点位定义保持一致。

响应 / 列表索引 本次请求的返回结果 / 结果中的位置

response.registers 是返回的寄存器值列表，[0] 取第一个完整的值。

注意：[653, 125][0] 得到 653，不是数字 6。

轮询 按节奏重复请求

采集器周期性询问设备当前值。

注意：当前实验只问一次；Modbus TCP 本实验的值变化不会主动推送给客户端。

数据库 / SQLite 保存和查询记录 / 本项目计划使用的数据库

每次成功采集的值和时间保存下来，形成历史。

注意：当前程序的寄存器内存不是历史数据库。SQLite 尚未接入。

后端 API / 前端看板 查询入口 / 用户看到的页面

目标：后端查询数据库，浏览器请求 API 后展示数值和曲线。

注意：打开页面不应创建新的采集循环；这两个模块尚未实现。

通信失败 / 超时 请求未成功 / 等待超过限制

可能是服务未启动、端口不一致、网络问题等，需要查证。

注意：失败意味着当前值未知，不能用 0 代替；本轮仅实测停止服务的连接拒绝。

新鲜度 / 过期 最后成功数据的年龄 / 超过项目阈值

教学规则：当前时间减最后成功采集时间 > 5 秒，则过期。

注意：新数据成功到来后重新判断，不是永久故障标签。

退出码 / 标准输出 / 标准错误 程序结果标识 / 正常结果通道 / 错误信息通道

当前客户端成功返回 0；通信失败返回 1，错误写入标准错误。

注意：参数非法由 argparse 返回 2；通信失败不应输出伪测量。

uv / 虚拟环境 / 锁文件 环境工具 / 项目依赖空间 / 固定依赖解析结果

uv run 使用项目环境；uv.lock 记录依赖版本等信息，--locked 要求配置与锁文件一致。

注意：本项目固定 Python 3.11.15 和 PyModbus 3.11.3；不代表它们是最新版。

学习笔记 / 06

失败、旧值与过期：三件事要分开

情况我们知道什么正确处理
成功读到 0本次测量为 0℃（按当前倍率）保存有效测量
请求失败当前温度未知记录失败，不新增假温度
旧值超过阈值保留的数据已经太旧显示最后已知值、原时间及过期标记

时间线：状态可以恢复

当前时刻发生的事最后成功时间数据状态
12:00:00成功读到 65312:00:0065.3℃ · 未过期
12:00:03连续读取失败12:00:003 秒旧 · 未过期，但通信失败
12:00:06仍无新数据12:00:006 秒旧 · 已过期
12:00:07成功读到 68112:00:0768.1℃ · 未过期
12:00:13之后一直没有新数据12:00:076 秒旧 · 已过期

教学配置：年龄 > 5 秒时过期，恰好 5 秒不算过期。新数据成功到来，相当于年龄回到 0。

数据年龄 = 当前时间 - 最后成功采集时间
是否过期 = 数据年龄 > 5 秒
# 没有任何成功记录：显示“暂无数据”，不虚构时间

最近尝试时间可以在失败时更新；最后成功时间只能在成功时更新。通信失败与新鲜度要分别展示。“连接失败就一定立即过期”不成立。

学习笔记 / 07

从真实代码到下一步伪代码

已实现：连接 → 请求 → 检查 → 换算

下面为当前客户端的核心代码摘录，省略命令行参数和异常处理，不是完整独立程序。

client = ModbusTcpClient("127.0.0.1", port=15020, timeout=2, retries=0)
if not client.connect():
    raise ConnectionError("无法连接")

response = client.read_holding_registers(0, count=1, device_id=1)
if response.isError():
    raise ModbusException("设备返回错误")
if len(response.registers) != 1:
    raise ModbusException("响应数量不符合预期")

raw = response.registers[0]
temperature = raw * 0.1
print(f"温度：{temperature:.1f}℃")

先检查响应再取数；:.1f 只控制显示为一位小数。完整程序在异常时输出错误并返回 1，最终关闭连接。

后续目标：持续采集（教学伪代码，不能直接运行）

每到一个采集时刻：
    记录最近尝试时间
    尝试：
        向设备读取温度寄存器
        检查协议响应与数据数量
        温度 = 原始值 × 倍率
        记录本次成功采集时间
        保存温度、单位、设备和时间
    如果通信失败：
        记录采集失败事件
        不写入 0，不重复保存旧值
        不更新最后成功采集时间
    等待下一个采集时刻

页面查询时：
    如果从未成功采集：显示“暂无数据”
    否则：显示最后已知值、原时间、通信状态和新鲜度
固定在每轮末尾 sleep(1) 会使周期包含通信和写库耗时；正式实现采样节奏时再处理。页面请求不能启动这个采集循环。

今天的疑问与解答

以下按主题复述本次可见对话，保留理解过程与纠正点，不把讲解过等同于已熟练掌握。

01 · 原始值要怎么表示 72.8℃？

对话记录：你回答 728，正确。

解答：倍率约定为 0.1，所以原始值 728 × 0.1 = 72.8℃。

02 · 停止模拟器后，页面上的旧温度怎么办？

对话记录：你指出要说明它是停止前的数据。

解答：保留最后已知值及原采集时间，并展示通信失败或过期状态，不能当作当前测量。

03 · 为什么打开第二个页面不能让采集频率翻倍？

对话记录：你最初不理解，随后理解了独立采集的用途。

解答：采集器是记录员，数据库是记录本，浏览器是读者。多一个读者只增加查询，不应增加记录员。

04 · 关掉浏览器，10 分钟的历史还会有吗？

对话记录：你回答应该有，并指出可以用于排查问题。

解答：目标架构下，只要采集器持续成功写库就会有；技术原因是采集独立运行。当前最小程序尚未存储历史。

05 · 读取失败后，能把旧值的时间更新为现在吗？

对话记录：你正确指出：采集失败不代表温度不变。

解答：不能。即使真实温度恰好没变，也没有本次成功测量作依据；失败不更新最后成功时间。

06 · 12:00:07 成功读到 681 后，仍然过期吗？

对话记录：你最初回答温度和时间正确，但认为仍已过期。

解答：应为 68.1℃、最后成功时间 12:00:07、未过期。此刻数据年龄为 0 秒。旧失败事件仍保留。

07 · 随后一直没新数据，到 12:00:13 呢？

对话记录：你正确回答：过期。

解答：距最后成功时间 6 秒，超过 5 秒阈值。恰好 5 秒时按当前 > 5 的规则尚未过期。

08 · 需要学多久才能开发？一定要亲自敲代码吗？

对话记录：你希望理解为主，也愿意阅读 AI 写的关键代码。

解答：采用小任务并行教学：AI 实现和验证，你通过解释数据流、预测输出、实验和排错证明理解。无需学完全部概念才开发。

09 · count=1 和 response.registers[0] 是什么？

对话记录：你正确理解 count 是读取数量，但对列表内容仍有疑问。

解答：count=1 是读一个寄存器，不是每秒读一次。[0] 是取返回列表第一个寄存器值，而不是这个数的第一位数字。

10 · 寄存器是什么？设备里有很多个吗？

对话记录：你提出了“编号数据格子”的核心疑问。

解答：设备可提供多个寄存器；地址是位置，点位表定义意义。多个格子可分别表示温度、电流，也可能组合表示同一个数。

11 · 为什么叫保持寄存器？断电还在吗？

对话记录：本次讲解澄清名称与保存能力的区别。

解答：它是 Modbus 数据区类型，协议支持读写；是否掉电保存取决于设备实现。当前模拟器数据放在内存里。

12 · 模拟器模拟的是 PLC、温控仪吗？PLC 是什么？

对话记录：你确认了真实设备与软件模拟的关系。

解答：模拟器扮演这些设备提供 Modbus 数据的接口端。PLC 是可编程逻辑控制器，按程序读取输入、判断和更新输出。

13 · 不断变化的寄存器数据就形成返回列表了吗？

对话记录：这里曾混淆横向的多个地址与纵向的多次采样。

解答：一次返回列表通常对应这次请求的多个连续寄存器；历史是采集器将多次成功结果带时间保存后形成的。

14 · lst[0] 就一定是地址 0 吗？

对话记录：你理解了列表由多个寄存器值组成，但把索引等同于绝对地址。

解答：仅当起始地址为 0 时成立。从地址 10 开始读取，lst[0] 对应 10，lst[1] 对应 11。地址 = 起始地址 + 索引。

失败后把旧值配上当前时间，会造成什么问题？

伪造一次成功采样，让页面误以为数据新鲜，历史趋势误以为温度稳定。

服务端恢复且读取成功后，过期状态怎么办？

按新的最后成功采集时间重新计算，此刻数据年龄约为 0，应恢复未过期。
